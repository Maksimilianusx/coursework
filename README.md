# Инфраструктура управления учетными записями пользователей

Учебный проект курсовой работы по дисциплине «Настройка и администрирование сервисного программного обеспечения». Автор: Шкуров Максим Дмитриевич, ИКБО-10-25.

Реализованы веб-интерфейс, серверный API и конфигурация контейнерной инфраструктуры. API выполняет CRUD **реальных учетных записей Keycloak**, а не только локальных карточек. Отдельная PostgreSQL хранит журнал административных действий. В исходном комплекте нет готовых паролей, сертификатов, облачного аккаунта или снимков якобы запущенного кластера.

**Статус на 10.11.2026:** локальный стенд Docker Desktop/WSL2 запущен по HTTPS. Прошли 33 модульные и компонентные проверки, 15 интеграционных проверок с настоящими Keycloak/PostgreSQL и 7 проверок резервного копирования, восстановления данных в отдельной БД и сохранности после перезапуска. В браузере проверены вход оператора/наблюдателя, создание, изменение, блокировка и отображение журнала. Временные проверочные аккаунты удалены. Проверка восстановления сравнивает контрольные данные, но не включает вход в восстановленный экземпляр Keycloak. Дополнительно проверен локальный Swarm из трех DinD manager-узлов: семь реплик, общий двухузловой кэш Keycloak, повторные 15 HTTP-сценариев и замена задачи API за 28,5 с. Все временные узлы удалены. Это не испытание физической отказоустойчивости. TOTP и облачный CD пока не подтверждены. Подробности: `docs/ACCEPTANCE.md` и `docs/evidence/`.

## Состав и границы решения

| Сервис | Назначение | Compose | Swarm после bootstrap |
|---|---|---:|---:|
| edge | Nginx, TLS, HTML/JS клиент, обратный прокси | 1 | 1 |
| api | Flask, проверка JWT, RBAC, Keycloak Admin REST | 1 | 2 |
| keycloak | Вход, учетные записи, роли, TOTP, события | 1 | 2 |
| app-db | PostgreSQL журнала административных операций | 1 | 1 |
| identity-db | PostgreSQL данных Keycloak | 1 | 1 |

Итого: пять постоянных контейнеров локально и семь в целевом кластере. Одноразовый `bootstrap` служит только для первичной настройки. Начальная конфигурация `stack.yml` запускает одну реплику Keycloak, чтобы первичная настройка прошла последовательно; после нее выполняется масштабирование до двух.

Целевая конфигурация предусматривает три Linux-узла Swarm в роли manager. Кворум из двух manager позволяет пережить потерю одного manager в плоскости управления. Реплики API и Keycloak размещаются на разных узлах. **Это не полная отказоустойчивость всего сервиса:** базы имеют по одной реплике с локальными томами, закрепленными на узле `state=primary`; edge имеет одну реплику. Потеря узла с БД останавливает операции до восстановления. Масштабирование PostgreSQL командой `replicas: 2` не создает репликацию БД и в проекте не используется.

Решение управляет учетными записями веб-сервисов. Оно не заменяет доменные входы Windows, GPO или AD DS. Публикация пользователям административной консоли Keycloak допускается только в доверенной учебной сети. В промышленном варианте административный доступ следует вынести в отдельный защищенный контур.

## Версии

Базовые образы закреплены: Keycloak `26.8.1`, PostgreSQL `17.11-bookworm`, Python `3.13.18-slim-bookworm`, Nginx `1.30.6-alpine`. Зависимости API: Flask `3.1.3`, PyJWT `2.15.1`, psycopg `3.3.6`, Gunicorn `26.2.0`. Теги проверены по первичным источникам при подготовке проекта; эти версии образов собраны и запущены локально. Для воспроизводимого производственного выпуска дополнительно фиксируют digest базовых образов, транзитивные зависимости и SHA сторонних CI actions после их проверки.

## Локальный запуск

Команды ниже предназначены для Bash в Linux или WSL. Нужны Docker Engine с Compose v2, Python 3 и OpenSSL. Для Docker Desktop следует включить Linux containers и WSL integration. Локальный Compose демонстрирует функции приложения, но не заменяет испытание трехузлового кластера.

1. Скопируйте проект в свой каталог. Откройте терминал в корне проекта. Запустите проверки:

   ```bash
   python3 scripts/verify_static.py
   python3 -m unittest discover -s tests -p test_core.py -v
   ```

   Для всех 33 тестов установите зависимости в отдельное окружение: `python3 -m venv .venv`, `source .venv/bin/activate`, `pip install -r api/requirements.txt`, затем `python -m unittest discover -s tests -v`. Тесты не выполняют сетевые запросы и не изменяют реальные учетные записи.

2. Создайте секреты и учебный сертификат:

   ```bash
   python3 scripts/generate_secrets.py
   ```

   Скрипт ничего не перезаписывает. На Linux каталог `secrets/` имеет права 0700; файлы паролей доступны процессам контейнеров через Compose bind mounts, но защищены закрытым родительским каталогом на хосте. TLS private key имеет права 0600. На Windows проверьте ACL папки: доступ должен быть только у владельца и администратора. Не помещайте секреты в Git, облачные папки общего доступа и снимки экрана.

3. Добавьте в hosts **компьютера с браузером** запись `127.0.0.1 iam.lab.test` для Docker Desktop; для удаленной ВМ укажите ее IP. Для Windows файл расположен в `C:\Windows\System32\drivers\etc\hosts`, изменение требует прав администратора. Имя `.test` предназначено для учебного окружения.

4. Импортируйте созданный `secrets/tls.crt` в доверенное хранилище только учебного компьютера/профиля браузера. Это самоподписанный сертификат на 30 дней, не публичный сертификат. Не отключайте проверку TLS в коде клиента. Для curl используйте `--cacert secrets/tls.crt`.

5. Соберите и запустите сервисы:

   ```bash
   docker compose config --quiet
   docker compose up -d --build
   docker compose ps
   docker compose --profile tools run --rm bootstrap
   curl --cacert secrets/tls.crt https://iam.lab.test/health/ready
   ```

   До bootstrap `/health/ready` может возвращать ошибку: realm еще не создан. Bootstrap ожидает готовность Keycloak, создает realm `course`, клиентов, роли, служебную учетную запись и три тестовых аккаунта. При повторе существующие аккаунты и их пароли сохраняются. Изменение `realm.json` само по себе не обновляет существующий realm: изменения выполняются через административную консоль или отдельную проверенную миграцию.

6. Откройте `https://iam.lab.test/`. Имена: `lab.operator` и `lab.viewer`. Их первоначальный временный пароль находится в `secrets/demo_password.txt`. После первого входа каждый пользователь задает собственный пароль. Для `lab.operator` также требуется настройка приложения TOTP по QR-коду Keycloak. Тестовая управляемая запись `student.demo` имеет тот же временный пароль и также требует его смены при первом входе.

7. Консоль: `https://iam.lab.test/auth/admin/`; realm master, начальный пользователь `bootstrap-admin`, пароль из `secrets/bootstrap_admin_password.txt`. После настройки создайте именованного администратора, проверьте его вход, затем удалите временного bootstrap-администратора. Не удаляйте единственный доступный административный аккаунт. При уничтожении bootstrap-аккаунта повторный bootstrap не сработает, что ожидаемо.

## Действия пользователя

`operator` читает список, создает записи, меняет имя/фамилию/почту, активирует или блокирует учетные записи и удаляет их после отдельного подтверждения. `viewer` читает список и журнал; сервер отклоняет его POST/PUT/DELETE с HTTP 403, даже если запрос сформирован вручную. Кнопки в интерфейсе не являются средством защиты.

При создании пользователь не получает пароль автоматически. В консоли Keycloak откройте realm `course`, раздел Users, нужного пользователя, Credentials, задайте временный пароль. Передайте его по согласованному защищенному каналу. После проверки первичного входа доступ можно активировать. Такая процедура отделяет создание профиля от передачи секрета. SMTP и автоматические приглашения в этом учебном проекте не настроены.

Маркер `managed_by=course-project` ограничивает область действий приложения. Через API нельзя менять credentials, роли, username существующего аккаунта и произвольные attributes. Операторы/наблюдатели и служебная учетная запись не имеют маркера и недоступны для CRUD через портал. Сервисный клиент Keycloak при этом имеет полномочия `manage-users`, `view-users`, `query-users` в учебном realm; это шире ограничений API. Маркер защищает от штатных запросов, но не заменяет fine-grained admin permissions при компрометации backend. Для промышленного решения требуется более строгая модель сервисных прав и отдельная проверка угроз.

Блокировка запрещает новый вход, после изменения профиля API отдельно отправляет запрос завершения пользовательских сессий. Если этот второй запрос не подтвержден, результат помечается `uncertain`. Уже выданный JWT, проверяемый API локально, может действовать до истечения 120 секунд. Завершение сессий препятствует дальнейшему обновлению сессии, но не является мгновенным отзывом ранее выданного access token. Для требований немедленного отзыва нужны проверка состояния/introspection или другой механизм отзыва. Автоматическое обновление токена здесь не реализовано: после двух минут интерфейс предлагает войти вновь.

## Кластер Swarm и облачный стенд

Подготовьте три Linux ВМ в одной закрытой сети. Проектные адреса можно принять `10.20.0.11`, `.12`, `.13`, но фактические адреса необходимо записать в протокол. Разумный начальный размер для учебного стенда: по 2 vCPU, 4 GiB RAM, 25 GiB диска. Это проектная оценка, не результат нагрузочного измерения. На всех узлах установите совместимые версии Docker Engine и синхронизацию времени.

Между узлами разрешите TCP 2377, TCP/UDP 7946, UDP 4789 и протокол IP 50 (ESP для encrypted overlay). Эти порты нельзя открывать всему Интернету. TCP 80/443 разрешается только для необходимых клиентов; TCP 22 — для администратора. PostgreSQL 5432, Keycloak 8080/9000 и API 8000 наружу не публикуются.

На первом узле:

```bash
docker swarm init --advertise-addr 10.20.0.11
docker swarm join-token manager
```

Команду `docker swarm join ...` с полученным токеном выполните на двух остальных ВМ. Не включайте join-token в курсовую или снимки. Затем на manager:

```bash
docker node ls
docker node update --label-add state=primary ИМЯ_ПЕРВОГО_УЗЛА
```

Метка `state=primary` должна быть ровно у одного узла. Она удерживает обе БД рядом с их локальными томами. При переносе метки без восстановления данных возникнет другой, пустой локальный том; это не допустимый способ восстановления.

Репозиторий проекта: https://github.com/Maksimilianusx/coursework. Workflow публикует образы в GHCR после успешных проверок; каталог `secrets/` исключен из Git. После сборки все узлы должны иметь возможность скачать образы. Вручную тот же выпуск можно собрать так:

```bash
export REGISTRY=ghcr.io/ВАШ_ЛОГИН/course
export IMAGE_TAG=ПОЛНЫЙ_SHA_КОММИТА
docker login ghcr.io
for component in api edge keycloak app-db identity-db; do
  context="$component"
  [ "$component" = app-db ] && context=database
  docker build -t "$REGISTRY/$component:$IMAGE_TAG" "$context"
  docker push "$REGISTRY/$component:$IMAGE_TAG"
done
python3 scripts/generate_secrets.py
sh scripts/create_swarm_secrets.sh
docker stack config -c stack.yml
docker stack deploy --with-registry-auth -c stack.yml course
sh scripts/bootstrap_swarm.sh
docker service logs course-bootstrap
docker service ps course-bootstrap --no-trunc
```

Проверьте, что одноразовая задача завершилась с exit code 0 (команда проверки выводится скриптом). Затем:

```bash
docker service rm course-bootstrap
docker service scale course_keycloak=2
docker stack services course
docker service ps course_keycloak
docker service ps course_api
```

Сохраните вывод и скриншоты. Для браузера измените hosts: `iam.lab.test` должен указывать на доступный адрес узла ingress. Внешняя схема/имя в Keycloak, realm client redirect URI и константа `ISSUER` API должны оставаться согласованными. Для другого домена измените их одновременно, пересоберите образы, замените сертификат и настройте DNS.

## CI/CD

Workflow запускает проверки на push/PR. На push в main и ручном запуске после проверок собирает пять образов и публикует их в GHCR с тегом SHA коммита. `docker stack deploy` не собирает образы и получает их из registry.

CD выполняется только через `workflow_dispatch` с `deploy=true` в ветке main. Предварительно нужны:

1. Защищенная ветка main и GitHub environment `lab` с одобрением развертывания.
2. Отдельный self-hosted runner Linux с label `course-lab` на доверенном manager. Docker-доступ runner эквивалентен административным правам на хост: нельзя отдавать такой runner непроверенным pull request.
3. Уже инициализированный Swarm, secrets, bootstrap и данные realm.
4. Доступ к GHCR; разрешения workflow на packages.
5. Файл доверенного учебного сертификата `/opt/course-lab/tls.crt` и разрешение `iam.lab.test` на runner.

После deploy job масштабирует Keycloak до двух реплик, выводит сервисы и ожидает успешный `/health/ready`. Этот smoke check не заменяет CRUD/RBAC/отказные испытания. URL облачной инфраструктуры и успешный pipeline должны быть подтверждены фактически. В комплекте нет выполненного облачного deploy.

Откат приложения: укажите предыдущий проверенный `IMAGE_TAG` и повторите deploy либо используйте `docker service rollback course_api`. Откат схемы БД не гарантируется откатом образа. Не выполняйте downgrade версии Keycloak/PostgreSQL без плана совместимости и отдельной резервной копии.

## Журнал и согласованность

Таблица `operations` содержит UUID операции, субъект JWT, действие, цель, время и статус. Пароли, bearer token, полный профиль и service secret не записываются в журнал. Сначала фиксируется `pending`, затем выполняется запрос Keycloak и записывается `succeeded`. При явном отказе фиксируется `failed`; при сетевой неопределенности — `uncertain`. Если заключительная запись недоступна, статус может остаться `pending`, а API сообщает необходимость сверки.

Транзакция PostgreSQL не охватывает Keycloak. При неопределенном результате нельзя автоматически повторять создание/удаление. Сначала проверьте наличие пользователя по логину/id, события Keycloak и журнал. Это ограничение распределенной операции, а не доказанная атомарность. Для промышленного варианта нужны идемпотентный журнал команд, reconciler и более полный учет отказов.

Учетная запись PostgreSQL `audit` не superuser: ей доступны SELECT/INSERT и обновление только столбцов `status`, `finished_at`. Keycloak использует отдельного владельца своей БД без superuser. Административные пароли БД не монтируются в API или Keycloak.

## Резервное копирование и восстановление

На узле `state=primary` перед изменением версии сделайте логические копии обеих БД. Для согласованного учебного контрольного состояния сначала остановите API и Keycloak, затем копируйте обе базы. Без остановки каждый dump согласован внутри одной БД, но общего транзакционного снимка двух БД нет. Для Compose:

```bash
mkdir -p backups
chmod 700 backups
docker compose stop api keycloak
docker compose exec -T app-db pg_dump -U postgres -d audit -Fc > backups/audit.dump
docker compose exec -T identity-db pg_dump -U postgres -d keycloak -Fc > backups/keycloak.dump
docker compose start keycloak api
```

Для Swarm на узле с БД найдите контейнеры по меткам сервиса и выполните `docker exec ... pg_dump` аналогично. Файлы содержат персональные данные и сведения аутентификации; храните их в защищенном месте вне единственного узла. Копии секретов храните отдельно. Realm export не заменяет полную резервную копию БД Keycloak.

Проверку восстановления выполняйте на **отдельном изолированном стенде** с теми же версиями и свежими томами, остановив API и Keycloak. Init-скрипт создаст пустую таблицу audit; поэтому при восстановлении учебной копии используйте `pg_restore -U postgres -d ... --clean --if-exists --no-owner --exit-on-error`, чтобы заменить созданные объекты содержимым dump. Эти параметры удаляют объекты в целевой БД, поэтому назначением должна быть именно выделенная тестовая копия. Для базы Keycloak восстановленные объекты должны принадлежать роли keycloak: используйте при восстановлении `--role=keycloak` (административное соединение postgres). Для audit после восстановления проверьте GRANT из `database/init-role.sh`. Затем включите Keycloak/API, проверьте вход, пользователей и журнал. Не выполняйте эти действия поверх работающей БД без отдельного плана восстановления.

Запишите реальное время копирования/восстановления и фактическую потерю данных в протокол. RPO/RTO в работе до испытаний являются целевыми значениями или не определены; измеренные показатели нельзя подменять оценками.

## Повторная проверка и оставшиеся действия

Для проверки работающего стенда выполните `python scripts/acceptance_http.py --secrets-dir secrets --output evidence/http-acceptance.json`. Сценарий создает два временных аккаунта и одну управляемую запись, проверяет OIDC Code + PKCE, CRUD, RBAC и журнал, затем удаляет только собственные тестовые объекты. Пароли и токены не попадают в отчет.

Локальные результаты и снимки приложены к курсовой. Для облачного CD еще необходим подготовленный Linux/Swarm-стенд и self-hosted runner с метками `linux`, `course-lab`; запуск `deploy=true` без них будет ожидать runner. Предоставление VPS не входит в исходный комплект. Проверку TOTP и отказов всего кластера нужно выполнить отдельно. Официальный отчет антиплагиата формирует студент в системе вуза.

Исправлены обнаруженные при испытаниях дефекты: Nginx теперь обновляет DNS-адреса контейнеров после их перезапуска; частичное обновление/блокировка пользователя сохраняет неизмененные поля профиля Keycloak. Эти сценарии включены в повторные проверки.

Для Swarm добавлена внутренняя зашифрованная сеть `cachenet` (`10.42.10.0/24`) и явный `KC_CACHE_EMBEDDED_NETWORK_BIND_ADDRESS`. Иначе Keycloak мог объявлять адрес локального docker_gwbridge, недоступный другой реплике. Если эта подсеть занята, измените одновременно IPAM и регулярное выражение bind-address. Фактическое объединение подтверждается `ISPN000094` с `(2)`, а не только счетчиком `2/2`. Одноразовый bootstrap запускается с `--no-healthcheck`: HTTP-healthcheck образа API для этого процесса неприменим.

На уже настроенном Windows-компьютере можно запустить `START_LAB.cmd` из папки приложения. Он использует существующие secrets и открывает сайт; для новой установки сначала выполните README.
